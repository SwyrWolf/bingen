# Calling Conventions

## Windows x86-64 Conventions
For integer(int 			/ i32) arguments: `ecx`, `edx`, `r8d`, `r9d`
For integer(long long / i64) arguments: `rcx`, `rdx`, `r8`, `r9`

> For arguments beyond 4, they'll exist on the stack. `rsp` (stack pointer) points to their location.

For return values:

- `int`, `long`, pointers, and similar scalar integer values return in `eax`/`rax`
- floating-point return values use XMM registers such as `xmm0`

This is why a function like this is valid:

```asm
.code

PUBLIC square

square PROC
	; Windows x64 ABI: first int argument is in ecx.
	; Return value for int is in eax.
	mov eax, ecx
	imul eax, ecx
	ret
square ENDP

END
```

For `square(int value)`, the caller places `value` in `ecx` and expects the result in `eax`.

## Register preservation rules

The Windows x64 ABI also says which registers a called function must preserve:

- Callee-saved: `rbx`, `rbp`, `rdi`, `rsi`, `r12`, `r13`, `r14`, `r15`
- Caller-saved: `rax`, `rcx`, `rdx`, `r8`, `r9`, `r10`, `r11`

This means a function may freely overwrite caller-saved registers, but must preserve callee-saved registers if it changes them.

## Stack use

The stack is still used for:

- stack locals
- saved return address
- extra arguments beyond the first four integer arguments
- alignment and shadow space

The function prologue and epilogue are not required for a tiny function like `square`, but more complex assembly will often push/pop registers and reserve local stack space.

## Why this matters for COFF and object files

The object file does not magically know the meaning of a register. 
The generated machine code and the linker contract together define the behavior. 
When a C++ function declaration and the assembly function agree on the same calling convention, 
the caller and callee match and the program links and runs correctly.
